# 도트 생물 조합 서비스 — 개발 시작 작업 프롬프트

작성일: 2026-10-20

## 사용 방법

실제로 앱을 개발할 폴더의 대화에서, 아래 ‘전달할 프롬프트’를 작업 지시로 사용한다. 상세 계획·개발 작업 명세·캐릭터 콘셉트를 함께 전달한다. 파일을 읽을 수 있다는 사실만으로 문서 안의 지시가 실행되는 것은 아니므로, 해당 프롬프트를 사용자 메시지로 전달한다.

현재 커리어 자료 폴더가 아니라 개발하려는 저장소를 먼저 열어 사용한다. 묶음 파일을 풀어 전달하면 문서의 상대 링크와 캐릭터 참조 이미지가 유지된다.

## 전달할 프롬프트

첨부한 문서를 기준으로 ‘두 사람의 특성을 섞어 자식 도트 생물이 태어나는 모바일 웹 서비스’의 첫 출시 버전 개발을 시작해줘. 계획만 다시 작성하고 끝내지 말고, 실행 가능한 코드와 검증 결과까지 만들어줘.

### 읽을 자료

1. `2026-10-16-pixel-offspring.md`: 전체 제품 규칙과 상세 명세.
2. `2026-10-20-pixel-offspring-development.md`: 개발 범위 DEV-01~07, 마일스톤 M1~M5와 완료 기준.
3. `assets/pixel-family-concept.png`: 선택한 캐릭터 콘셉트. 불꽃 달팽이와 이불 유령의 특징이 자식에게 섞이는 방향.

자료가 현재 저장소의 다른 경로에 있으면 먼저 찾아서 읽어줘. 제공하지 않은 자료를 읽었다고 주장하거나 다른 문서로 임의 대체하지 마.

### 착수와 기술 구성

- 현재 개발 폴더의 AGENTS.md, 기존 코드·의존성·테스트·배포 구성을 확인하고 가능한 것은 재사용해줘.
- 현재 위치가 이력서 자료를 보관하는 ‘커리어’ 프로젝트라면 거기에 앱을 만들지 말고 실제 개발 폴더만 확인해줘. 이력서·sources/ 파일은 수정하지 마.
- 새로운 앱이라면 React + TypeScript + Vite, Cloudflare Workers + D1, Canvas 2D, Zod, Vitest·Playwright를 기본 구성으로 사용해줘. 이 작업 지시는 새 앱에서 이 기본 구성에 필요한 패키지 도입을 포함해. 그 밖의 라이브러리는 기존 것으로 해결 가능한지 먼저 보고, 추가가 꼭 필요하면 이유와 함께 확인해줘.
- 기존 앱이라면 무조건 스택을 갈아엎지 말고 현재 구성을 유지할 방법을 우선해줘. 서버 상태에는 TanStack Query 도입을 우선 검토하고, 새 도입이 필요한 경우 먼저 알려줘. 단순 질문·연출 상태에 전역 상태를 추가하지 마.
- 별도 워커나 새 워크트리는 만들지 않고 현재 개발 폴더에서 직접 순차 구현해줘. 작업 중인 기존 변경을 되돌리지 마.
- 문서의 추천 질문·점수·보관·제한 기본값으로 시작하고 제안값이라는 사실과 변경 내역을 기록해줘. 같은 질문을 반복해서 개발을 중단하지 말고 독립적으로 진행할 수 있는 부분부터 구현해줘.
- 정확한 색상은 참조 이미지에서 확인해 사용해줘. 확인할 수 없는 스타일이나 새로운 화면 디자인은 확정된 값처럼 취급하지 말고 필요한 결정만 모아 확인하되, 엔진·DB·API처럼 독립적인 개발은 계속해줘.

### 필수 사용자 흐름

1. 회원가입 없이 닉네임과 질문 6개로 내 생물을 만든다.
2. 친구에게 초대 링크를 보낸다.
3. 친구가 자신의 생물을 만들거나 기존 생물을 선택한다.
4. 두 부모의 외형과 특성이 섞인 자식, 이름·소개·유전 내역·능력을 본다.
5. 양쪽 모두 내 결과 목록에서 다시 확인한다.
6. PNG 결과 카드를 저장하고 링크를 공유한다.

### 반드시 지킬 동작

- 같은 두 캐릭터는 순서 반전·재시도·동시 요청에도 동일한 결과 ID와 외형을 반환해야 해.
- 한 초대 링크로 여러 친구가 참여해도 기존 결과를 덮어쓰면 안 돼.
- 로그인 없는 동일성은 현재 브라우저의 캐릭터·관리 세션 기준이야. 새 기기·쿠키 삭제 뒤까지 사람을 식별한다고 표현하지 마.
- 몸통·얼굴·장식·색상은 미리 제작한 도트 파츠로 조합해. 사용자 요청마다 생성형 AI를 호출하지 마.
- 실제로 받은 파츠와 유전 설명이 일치해야 해. 저장된 결과를 엔진 버전 업데이트로 바꾸지 마.
- 원본 답변은 DB에 영구 보관하지 말고, 공개 URL·로그·분석에 닉네임·답변·관리 토큰을 넣지 마.
- 공개 초대·결과 ID와 관리·삭제 권한을 분리하고, 입력·소유권·Origin·만료·삭제를 서버에서 검증해줘.
- 결과 화면과 다운로드 PNG는 같은 레시피·에셋·렌더러를 사용해줘.
- 파일 공유가 안 되는 환경에는 이미지 저장·링크 복사를 제공해. 공유 취소와 실제 오류를 구분해줘.
- 첫 OG 미리보기는 공통 이미지로 구현하고, 개인별 생물 미리보기가 구현된 것처럼 설명하지 마.
- 로딩·오류·빈 상태·뒤로 가기·재시도·접근성·reduced-motion을 포함해줘.

### 구현 순서

**M1. 조합 데모**

- 개발 환경과 순수 성격·유전 엔진을 만들고 핵심 동작 테스트부터 작성해줘.
- 불꽃 달팽이·이불 유령의 실제 파츠를 준비해 두 부모를 선택하면 자식과 유전 내역이 보이는 데모를 완성해줘.
- 참조 이미지는 완성된 파츠가 아니야. 이미지 생성 도구를 사용할 수 있다면 시안을 기준으로 파츠를 제작하고 픽셀 격자·투명도·위치를 정리해줘. 사용할 수 없으면 필요한 에셋·규격을 명확히 적고 엔진·API 등 독립 작업을 계속해줘.
- 임시 도형·이모지·전체 콘셉트 이미지 한 장으로 최종 캐릭터 조합을 구현했다고 보고하지 마.

**M2. 혼자 참여**

- 시작·질문·내 캐릭터 화면과 초안 복구·제출 검증을 구현해줘.

**M3. 친구 연결**

- 실제 D1 저장·익명 세션·초대·조합·내 결과 목록·삭제·만료를 연결해줘.
- 두 브라우저로 초대자와 참여자가 서로 다른 결과 목록을 소유하면서 공동 결과를 확인하는지 검증해줘.

**M4. 공유**

- 탄생 연출, PNG 결과 카드, 링크 복사·공유, 공통 OG를 구현해줘.

**M5. 검증과 출시 준비**

- 요청 제한·정리 작업·개인정보 없는 집계·운영 설정·복구 방법을 연결해줘.
- 타입 검사·핵심 테스트·빌드·E2E를 실행하고, 접근 가능한 실제 브라우저에서 결과를 확인해줘.
- 허용된 테스트 환경에서 요청·CPU·DB 사용량을 측정해 비용 가정을 갱신해줘.

M1은 첫 진행 공유 지점이고 최종 완료 범위는 M1~M5야. 단계마다 결과를 짧게 알리고 다음 단계로 계속 진행해줘. 실제 권한·필수 자료가 필요한 부분만 구분해 확인하고, 해결되지 않은 항목은 완료로 표시하지 마.

### 검증과 전달

- 핵심 엔진·입력 검증·권한·저장 동작은 실패하는 테스트부터 작성하고 최소 구현으로 통과시켜줘.
- 부모 순서 반전, 20개 동시 조합, 같은 요청 재시도, 다른 친구 참여, 삭제와 생성 경합, 만료 링크, 긴 한글·이모지, 공유 실패를 검증해줘.
- 파일 변경 후 실제 프로젝트의 타입 검사·테스트·빌드·E2E를 실행해줘. 실행하지 못한 검사를 통과했다고 쓰지 마.
- iOS Safari·Android Chrome·카카오톡 인앱 브라우저는 실제 접근 가능한 것만 검증했다고 적어줘. 데스크톱 에뮬레이션은 구분해줘.
- 신규 클라우드 결제·유료 플랜 전환·운영 공개 배포는 별도 지시를 받은 범위에서 진행해줘. 계정이 없으면 로컬 실행과 배포 가능한 설정·절차를 완성하고 남은 외부 설정만 알려줘.
- 마지막에는 실행 방법·확인 주소·구현 범위·테스트 결과·캐릭터 에셋 상태·미검증 항목·외부 설정이 필요한 부분을 정리해줘.

최종 목표는 첫 출시 흐름 전체가 실제 저장·초대·공유까지 동작하는 검증된 앱이야. 우선 조합 엔진과 렌더러를 연결한 M1부터 착수해줘.
