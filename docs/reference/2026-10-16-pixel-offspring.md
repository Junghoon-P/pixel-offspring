이 문서는 기획부터 출시까지 한 파일에서 확인하는 실행 계획이다. 대화에서 선택한 서비스·캐릭터 방향은 유지한다. 질문, 점수, 파츠 수, 기간, 요청 제한, 카드 크기 등 아래 상세 수치는 개발을 구체화하기 위한 추천 기본값이며 아직 사용자 확정 사항은 아니다. 구현 완료나 일정·비용 보장을 의미하지 않는다.

**Goal:** 회원가입 없이 자신의 도트 생물을 만들고 친구와 조합해, 두 사람의 특성이 보이는 자식 생물과 결과 카드를 공유한다.

**Architecture:** React 정적 화면과 도트 파츠를 Cloudflare Workers로 제공하고, 초대·조합·조회 API와 D1으로 결과를 보관한다. 캐릭터와 설명은 버전이 고정된 파츠·문구 조합으로 생성하며 사용자 요청마다 생성형 AI를 호출하지 않는 구성을 제안한다.

**Tech Stack:** 제안 구성은 React, TypeScript, Vite, Cloudflare Workers, D1, Canvas 2D, Zod와 테스트 도구 Vitest·Playwright. 구현 전 기존 개발 저장소와 의존성을 확인하고, 신규 패키지는 사용자에게 구성을 설명한 뒤 승인 범위에서 도입한다. 버전은 구현 시 공식 가이드와 호환성을 확인해 잠금 파일에 고정한다.

**Spec:** 이 문서의 ‘제품 기준’ 및 현재 대화에서 선택한 불꽃 달팽이 + 이불 유령 시안. 상세 정책 중 ‘제안’으로 표시한 것은 사용자 확정 사항과 구분한다.

- 실제 구현은 별도 앱 저장소에서 시작하는 것을 제안한다. 저장소 위치와 실행 방식은 착수 때 정한다.
- sources/는 읽기 전용이며 이번 작업의 변경 대상이 아니다.

## 제품 기준

### 대화에서 선택한 방향

- 두 사람의 성격으로 만든 캐릭터를 합쳐 새로운 도트 생물이 탄생한다.
- 결과에는 생물 이름, 짧은 성격 설명, 각 부모에게 받은 특징, 웃긴 특수 능력이 보인다.
- 시각 기준은 불꽃 달팽이·이불 유령·불꽃 이불 달팽이 콘셉트 시안이다.
- 서버리스 운영과 낮은 유지비를 고려한다. 앞서 제시한 월 1만원은 초기 예산 목표이며 보장된 요금이 아니다.

### 첫 출시 제안

- 모바일 웹 우선, 회원가입 없이 시작한다. 초대 링크를 받은 친구도 질문에 답해 참여한다.
- 화면은 시작 → 질문 → 내 생물 → 초대 참여 → 탄생 → 결과의 6개 상태로 구성한다.
- 같은 초대 링크로 여러 친구가 참여하며 친구마다 별도 조합 결과가 생긴다.
- 동일한 두 캐릭터는 참여 순서·새로고침·동시 요청과 관계없이 같은 결과 ID로 연결한다.
- ‘같은 사람’은 첫 버전에서 같은 브라우저에 보관된 캐릭터 ID로 식별한다. 새 기기·쿠키 삭제·새 캐릭터 생성까지 동일 인물로 판별하지 않는다.
- 성격 질문은 가벼운 오락 콘텐츠이며 실제 성격·관계 진단처럼 표현하지 않는다.
- 자식 재교배, 족보, 결제, 랭킹, 사진 업로드는 첫 출시 범위에서 제외하는 안이다.
- 질문 6개, 2지선다를 시작안으로 제안한다. 최종 질문·문구·보관 기간·요청 제한값은 1단계에서 화면과 함께 제시한다.

## Global Constraints

- 사용자에게 설명과 화면 문구를 한국어로 제공한다.
- 신규 라이브러리를 명시적인 요청 없이 추가하지 않는다. 이 계획의 스택은 도입 제안이다.
- TypeScript any 금지, 외부 입력 Zod 검증, 함수는 화살표 함수와 명시적 반환 타입을 사용한다.
- 함수 50줄 이하, 코드 파일 300줄 이하, console.log·TODO/FIXME 금지.
- 사용자 답변과 닉네임을 URL·분석 이벤트·운영 로그에 담지 않는다. 공개 결과에는 공유 대상으로 안내한 닉네임과 결과만 노출한다.
- 시크릿은 환경 설정으로 보관하고 D1 쿼리는 파라미터화한다.
- 이미지 시안은 완성된 게임 파츠가 아니다. 실제 파츠는 동일한 픽셀 격자·앵커·외곽선 규칙으로 정리한다.
- 디자인 수치와 색상은 승인된 디자인 원본에서 확인해 기록한다. Figma를 제공받으면 해당 수치를 우선하며 추측으로 매핑하지 않는다.
- 서버 상태를 클라이언트 전역 상태에 중복 저장하지 않는다. 로컬 질문 진행 상태는 로컬 상태로 처리한다.
- 새 기능의 핵심 동작을 먼저 테스트하고 구현한다. 다중 파일 변경 뒤 타입 검사와 빌드를 실행한다.

## 상세 명세 A. 사용자 흐름과 화면

### A-1. 초대하는 사람

1. 시작 화면에서 서비스 예시와 공개되는 정보를 읽는다.
2. 닉네임을 정하고 질문 6개에 답한다.
3. 내 캐릭터, 이름, 특성을 확인한다.
4. 초대 링크를 복사하거나 휴대폰 공유 창을 연다.
5. 같은 브라우저의 ‘우리 생물들’에서 친구가 만든 결과를 확인한다.

### A-2. 초대받은 사람

1. /i/:inviteId에서 상대의 닉네임과 캐릭터를 확인한다.
2. 내 캐릭터가 있으면 재사용하고, 없으면 질문을 진행한다. 질문 중에도 inviteId를 유지한다.
3. ‘우리 생물 만들기’를 누르면 서버가 두 캐릭터를 조합한다.
4. 저장 성공 후 탄생 연출을 보여주고 결과로 이동한다.
5. 카드 저장·링크 공유 후 자기 초대 링크도 만들 수 있다.

### A-3. 화면 상태

| 화면·주소 | 주요 내용 | 기본 동작 | 오류·빈 상태 |
| --- | --- | --- | --- |
| 시작 / | 부모와 자식 예시, 짧은 설명 | 내 생물 만들기 | 예시 이미지 실패 시 설명·시작 버튼 유지 |
| 질문 /create | 닉네임, 진행률, 질문·선택지 | 이전·다음·완료 | 미응답 위치 안내, 전송 실패 시 답변 유지 |
| 내 생물 /me | 내 생물, 초대 버튼, 우리 생물들 | 초대·기존 결과 열기 | 결과 0개면 초대 안내, 세션 없으면 시작 안내 |
| 초대 /i/:inviteId | 상대 생물, 내 생물 또는 참여 안내 | 내 생물 생성·조합 | 자기 초대·만료·삭제·없는 링크 구분 |
| 탄생 상태 | 두 부모, 짧은 연출 | 건너뛰기·결과 보기 | 저장 실패 시 연출을 시작하지 않고 재시도 |
| 결과 /r/:resultId | 부모 2개, 자식, 유전 설명, 능력 | 카드 저장·공유·나도 만들기 | 만료·삭제 안내, 링크 복사 대안 |

- 탄생은 별도 영구 URL 대신 조합 완료 뒤의 화면 상태로 구현한다. /r/:resultId 직접 진입은 결과부터 보여준다.
- 내 결과 목록은 20개씩 페이지 단위로 조회하고 최신순으로 표시한다. 페이지 이동 후에도 다른 친구의 결과가 섞이거나 누락되지 않게 (createdAt, id) 커서를 사용한다.
- 초대자는 /me 진입·창 재활성화·수동 새로고침 때 목록을 다시 읽는다. 첫 버전에는 상시 폴링이나 실시간 연결을 도입하지 않는다.
- 닉네임과 결과는 링크를 아는 사람에게 보인다고 생성 전에 안내한다. 공개 결과에는 검색엔진 색인을 막는 noindex를 적용하되 접근 권한 보호 수단으로 여기지 않는다.

## 상세 명세 B. 질문과 점수표

### B-1. 6문항 초안

오락용 질문이다. 선택지 ID는 a·b로 고정하며 표시 문구를 다듬더라도 기존 quizVersion의 점수는 바꾸지 않는다.

| ID | 질문 | 선택 a: -1 | 선택 b: +1 | 축 |
| --- | --- | --- | --- | --- |
| q1 | 갑자기 쉬는 날이 생겼다! | 이불 속에 자리 잡기 | 처음 가는 동네 탐험하기 | adventure |
| q2 | 메뉴판에 낯선 음식이 보이면? | 늘 먹던 메뉴가 좋다 | 궁금하니까 도전한다 | adventure |
| q3 | 친구들과 신나게 놀고 집에 오면? | 충전 시간이 필요하다 | 아직 더 놀 수 있다 | energy |
| q4 | 주말에 하고 싶은 일이 세 개 생겼다! | 하나만 하고 나머지는 다음에 | 일단 세 개 다 해본다 | energy |
| q5 | 여행 갈 때 나는? | 동선부터 정리한다 | 가서 마음 가는 대로 간다 | spontaneity |
| q6 | 갑자기 친구가 만나자고 하면? | 오늘 계획부터 확인한다 | 재미있겠다, 일단 나간다 | spontaneity |

- 각 축은 해당 2문항 점수의 합을 2로 나눠 -1·0·1 중 하나가 된다. 모든 문항이 정확히 한 번 있어야 한다.
- energy의 낮음·높음은 캐릭터 묘사를 위한 표현이며 능력이나 가치의 우열로 쓰지 않는다.
- 64가지 답변 패턴이 모두 유효한 부모 레시피로 변환되는지 전수 검사한다.

### B-2. 부모 기본 몸통 매핑안

| adventure | energy ≤ 0 | energy > 0 |
| --- | --- | --- |
| -1 | 이불 유령 | 말랑 젤리 |
| 0 | 버섯 | 작은 새 |
| 1 | 달팽이 | 꼬마 용 |

- 표정은 energy와 spontaneity, 장식은 adventure와 spontaneity를 우선 반영한다.
- 축이 같은 답변 패턴도 고정된 답변 시드로 색상·세부 파츠에 차이를 줄 수 있다. 부모 생성은 선택값만으로 재현 가능하게 한다.
- 이 매핑은 시안의 달팽이·유령을 포함하기 위한 초안이다. 시각 검증에서 더 잘 어울리는 연결이 나오면 v1 확정 전에 바꾼다.

## 상세 명세 C. 캐릭터 에셋

### C-1. 제작 규격안

| 항목 | 제안 규격 |
| --- | --- |
| 원본 격자 | 64×64px, 투명 PNG, 모든 파츠 같은 캔버스 크기 |
| 기본 표시 | 192×192px 또는 256×256px의 정수 배율 |
| 확대 방식 | nearest-neighbor, imageSmoothingEnabled=false |
| 외곽선 | 기준 격자 1px, 색상은 승인된 에셋에서 확정 |
| 렌더링 순서 | 뒤 장식 → 몸통 → 얼굴 → 앞 장식 |
| 장식 슬롯 | rear, head, wrap; 몸통별 앵커와 허용 슬롯 등록 |
| 색상 | 몸통·얼굴·장식별 승인된 공통 팔레트로 사전 출력 |
| 산출물 | 편집 원본, 투명 파츠, 카탈로그, 조합 미리보기, 출처·이용 조건 |

- 초기에는 불꽃 달팽이와 이불 유령에 필요한 파츠로 조합 가능성을 확인한다. 나머지 4종의 몸통은 확인 후 추가한다.
- 몸통 6종·표정 8종·장식 12종·색상 8세트는 제작 목표다. 파츠 수를 단순 곱한 값을 유효하거나 독창적인 캐릭터 수라고 홍보하지 않는다.
- AssetCatalog는 id, category, compatibleBodyIds, slot, zIndex, 몸통별 앵커, 색상별 파일 경로를 갖는다. 지정된 파일과 좌표가 없는 조합은 생성하지 않는다.
- 이불은 달팽이 껍질 일부를 가려도 나선이 남도록 제작한다. 서로 충돌하는 장식은 compatibleBodyIds와 슬롯 규칙으로 사전에 제외한다.
- 생성된 콘셉트 이미지를 자동으로 잘라 곧바로 운영 파츠로 쓰지 않는다. 실제 격자·투명도·팔레트와 조합 위치를 정리한다.
- 같은 외형을 가진 두 부모의 경우 시각적 차이를 억지로 만들지 않고, 유전 내역에 양쪽 출처를 표시한다.

### C-2. 시각 검수

- 64가지 부모 답변 패턴의 렌더링을 한 장씩 확인한다.
- 64×64=4,096가지 부모 답변 조합의 고정 테스트 데이터를 생성해 레시피 유효성을 자동 확인한다. 이는 모든 실제 캐릭터 ID 시드를 전수 검사한 것은 아니다.
- 모든 몸통×표정과 허용된 장식 조합을 별도 이미지 목록으로 확인한다. 큰 조합은 분할 시트로 검수한다.
- 승인 시안, 기본 부모 6종, 조합 결과 12쌍을 육안 비교하고 변경 이력을 남긴다.

## 상세 명세 D. 유전 엔진과 결과 문구

### D-1. 결과 생성 순서

1. 서버가 두 캐릭터의 유효성·공개 가능 상태를 확인한다. 자신의 동일 캐릭터 조합은 409로 거부한다.
2. characterId를 정렬해 parentLowId·parentHighId를 만든다. 표시 순서와 무관하게 이 두 값으로 기존 결과를 조회한다.
3. 기존 결과가 있으면 저장된 스냅샷과 ID를 반환한다. engineVersion이 변경돼도 재생성하지 않는다.
4. 없으면 SHA-256으로 두 ID와 engineVersion=1을 해시한다. 바이트를 body·face·decoration·palette·copy의 이름별로 분리해 선택한다.
5. 몸통은 한 부모, 얼굴은 다른 부모에서 받는다. 몸통을 준 쪽과 얼굴을 준 쪽의 원래 characterId를 기록한다.
6. 양쪽 부모의 장식을 호환 슬롯에서 우선 선택한다. 충돌하면 양쪽 출처를 유지할 수 있는 다른 슬롯·등록된 대응 파츠를 선택하고, 없으면 추가 장식을 생략한다.
7. 자식 성격 축은 두 부모 값의 산술 평균으로 계산한다. 평균값은 -1~-0.5~0~0.5~1의 범위에서 문구 선택에 사용한다.
8. 이름·짧은 설명·특수 능력·유전 내역을 만들고, 모든 파츠·문구 ID 검증 후 DB에 저장한다.

- 무작위 재시도나 Math.random으로 파츠를 고르지 않는다. 호환 목록은 카탈로그 순서에 고정한다.
- 같은 닉네임은 같은 사람을 뜻하지 않는다. 쿠키 삭제·새 기기·새 캐릭터 생성 후 이전 인물을 복구하거나 동일 인물로 식별하는 기능은 첫 버전에 없다.
- 조합 규칙·파츠·문구 묶음은 engineVersion·assetVersion·copyVersion으로 식별하고, 저장된 결과가 참조하는 이전 에셋을 보관 기간 동안 유지한다.

### D-2. 결과 카드 필드

| 필드 | 내용·규칙 |
| --- | --- |
| 부모 | 닉네임·원래 캐릭터 이미지 2개 |
| 자식 이름 | 장식 수식어 + 몸통 이름, 최대 20개 사용자 인식 문자 |
| 소개 | 행동이 그려지는 짧은 문장, 최대 60개 사용자 인식 문자 |
| 유전 내역 | parentId, 실제 받은 partId, 공개용 라벨 |
| 특수 능력 | 평균 성격 축과 대비 조합을 활용, 최대 40개 사용자 인식 문자 |
| 결과 ID | 조합별 무작위 공개 ID, 답변·닉네임을 포함하지 않음 |

예: ‘불꽃 이불 달팽이’ / ‘모험은 하고 싶고, 이불은 못 놓고’ / ‘여행 계획만 세우고 집에 있기’.

- 웃긴 문구는 미리 작성한 템플릿에서 고른다. 조합당 텍스트 생성 API는 호출하지 않는다.
- 같은 축끼리 만난 경우와 반대 축끼리 만난 경우를 모두 준비한다. 인격 비하·진단·관계 우열·외모 평가 표현은 제외한다.
- 고정 예시 12쌍에서 이름, 유전 내역, 실제 그림, 능력 설명이 서로 일치하는지 검토한다.

## 상세 명세 E. 데이터와 보관

### E-1. D1 테이블

| 테이블 | 주요 필드 | 제약·조회 인덱스 |
| --- | --- | --- |
| sessions | id, tokenHash, createdAt, expiresAt, deletedAt | tokenHash UNIQUE, expiresAt |
| characters | id, ownerSessionId, nickname, traitsJson, recipeJson, quizVersion, assetVersion, createdAt, expiresAt, deletedAt | ownerSessionId·createdAt, expiresAt |
| invites | id, characterId, ownerSessionId, createdAt, expiresAt, deletedAt | characterId의 활성 초대 조회, expiresAt |
| results | id, parentLowId, parentHighId, parentSnapshotsJson, childJson, engineVersion, assetVersion, copyVersion, createdAt, expiresAt, deletedAt | UNIQUE(parentLowId,parentHighId), 부모별 createdAt·id |
| request_keys | ownerSessionId, operation, key, payloadHash, resourceId, expiresAt | UNIQUE(ownerSessionId,operation,key), expiresAt |
| daily_metrics | day, event, count | PRIMARY KEY(day,event) |

- ID는 서버에서 암호학적으로 안전하게 생성한다. 외래 키를 적용하고 parentLowId < parentHighId를 제약으로 확인한다.
- JSON 필드는 읽을 때도 저장 버전에 맞춰 검증한다. 원본 답변은 영구 저장하지 않고 특성 점수와 레시피를 저장한다.
- 캐릭터는 생성 후 불변이다. 다시 답하면 새 캐릭터가 생기며, 기존 초대·결과를 새 캐릭터로 덮어쓰지 않는다.
- 모든 SQL은 prepare·bind를 사용한다. 여러 쓰기를 한 번에 처리할 필요가 있으면 D1 batch의 트랜잭션 동작을 사용한다. [D1 공식 문서](https://developers.cloudflare.com/d1/worker-api/d1-database/)
- request_keys는 캐릭터 생성 등의 재시도 중복 방지용이다. 같은 키와 다른 payload는 409를 반환한다. 키 보관안은 24시간이다.

### E-2. 보관·삭제 기본값안

- 관리 세션과 캐릭터는 생성 후 최대 90일, 초대는 생성 후 최대 30일 보관한다.
- 초대 expiresAt은 생성일+30일과 부모 캐릭터의 만료일 중 이른 값이다.
- 결과 expiresAt은 생성일+90일, 두 부모 만료일, 두 부모 세션 만료일 중 가장 이른 값이다. 부모가 먼저 만료되면 결과의 이용 기간도 짧아질 수 있음을 안내한다.
- /me에서 자신의 캐릭터를 삭제하면 그 캐릭터와 관련 초대·공동 결과를 즉시 비공개 처리한다. 상대도 공동 결과를 더 이상 조회하지 못한다는 안내를 삭제 전에 표시한다.
- 개인정보가 담긴 스냅샷은 조회 시 부모의 삭제 상태를 확인해 차단한다. 물리 정리는 매일 예약 실행하며 비공개 전환 후 24시간 이내 삭제를 목표로 한다.
- 삭제·만료 행이 남아 있는 동안 410, 물리 삭제 후와 처음부터 없는 ID는 404를 반환한다. 둘 다 복구할 수 없는 링크라는 사용자 안내로 연결한다.
- 백업의 보존은 제공자의 정책과 별도로 검토한다. 운영 데이터 삭제가 백업 즉시 삭제를 뜻한다고 표현하지 않으며, 복원 시 삭제 이력이 다시 공개되지 않게 확인한다.

## 상세 명세 F. API 계약

### F-1. 공통 계약

- QuizAnswers: { questionId, optionId }의 배열. 문항 6개가 각각 정확히 한 번 포함되고 다른 키·선택값은 거부한다.
- QuizSubmission: quizVersion, nickname, answers, idempotencyKey. 캐릭터 생성 시 서버가 점수·레시피를 다시 계산한다.
- CharacterView: id, nickname, traits, recipe, assetVersion, createdAt, expiresAt. tokenHash·관리 세션은 반환하지 않는다.
- InviteView: id, url, expiresAt. InviterPreview: 초대한 캐릭터의 id·nickname·recipe·assetVersion과 inviteExpiresAt만 포함한다.
- ParentSnapshot: characterId, nickname, traits, recipe, assetVersion. OffspringResult: 두 ParentSnapshot, 자식 recipe·이름·소개·능력·유전 내역과 버전 필드.
- PairView: resultId, resultUrl, created, expiresAt. PublicResult: resultId, 부모의 공개 필드, 자식 외형·문구·유전 내역·버전·만료일. 부모의 내부 성격 점수·세션·원본 답변을 제외한다.
- /api/me/results의 항목은 PairView에 부모 닉네임·자식 이름·미리보기 recipe를 추가한 ResultListItem이며 { items, nextCursor } 형태의 ResultListPage로 응답한다.
- 성공은 { data }, 오류는 { error: { code, message, retryAfterSeconds? } } 형태다. HTTP 상태와 오류 code를 함께 처리한다.

### F-2. 엔드포인트

| 메서드·경로 | 입력 | 성공 | 주요 거부 조건 |
| --- | --- | --- | --- |
| POST /api/session | 없음 | 200, 관리 쿠키 설정·재사용 | Origin 불일치, 세션 생성 과다 |
| POST /api/characters | QuizSubmission | 201, 재시도는 200 CharacterView | 400 입력 오류, 401 세션 없음, 409 키 충돌 |
| POST /api/invites | characterId, idempotencyKey | 201, 기존 활성 초대는 200 InviteView | 403 타인 소유, 410 삭제·만료 |
| GET /api/invites/:id | 경로 ID | 200 InviterPreview | 404 또는 410 |
| POST /api/invites/:id/pair | 내 characterId | 201, 기존 조합은 200 PairView | 403 소유권, 409 자기 조합, 410 만료 |
| GET /api/results/:id | 경로 ID | 200 PublicResult | 404 또는 410 |
| GET /api/me/characters | 관리 쿠키 | 200 CharacterView[] | 401 세션 없음 |
| GET /api/me/results | limit≤20, cursor? | 200 페이지 응답 | 400 잘못된 커서, 401 세션 없음 |
| DELETE /api/me/characters/:id | 관리 쿠키 | 204, 소유자 재시도도 204 | 403 소유권, 404 존재하지 않음 |
| POST /api/events | 허용된 이벤트 이름 | 202 | 400 등록되지 않은 이름·추가 필드 |

- 모든 API에 429 요청 제한과 503 일시 장애 처리를 적용한다. 읽기 실패와 쓰기 실패의 재시도 동작을 구분한다.
- 요청 본문은 최대 8KB로 제한하고 초과 시 413을 반환한다. Content-Type은 application/json만 허용한다.
- nickname은 NFC 정규화·앞뒤 공백 제거 후 1~12 grapheme으로 검증하고 제어문자·줄바꿈·방향 제어문자를 거부한다. 평범한 문자열로 렌더링하고 HTML로 해석하지 않는다.

### F-3. 동시 조합과 중복 방지

1. 기존 결과를 조회하고, 없으면 같은 규칙으로 후보를 계산한다.
2. UNIQUE(parentLowId,parentHighId)를 대상으로 충돌 시 새 행을 만들지 않는 INSERT를 수행한다.
3. 부모 유효성을 조건부 쓰기와 같은 D1 batch 안에서 확인해, 삭제와 조합의 경합에서도 삭제된 부모의 결과가 공개되지 않게 한다.
4. 저장된 행을 다시 읽어 반환한다. 응답을 잃고 다시 요청해도 기존 resultId를 돌려준다.
5. 새로 생성한 경우에만 pair_created를 집계한다. DB 쓰기 실패를 성공으로 감추거나 클라이언트에서 임의 결과를 확정하지 않는다.

## 상세 명세 G. 관리 권한과 요청 제한

- 관리 쿠키 이름안은 __Host-creature_session이다. Path=/, HttpOnly, Secure, SameSite=Lax를 설정하고 Domain 속성은 넣지 않는다. HTTP 로컬 개발에서는 별도 개발 쿠키 이름을 사용한다.
- 256비트 관리 토큰을 생성하고 DB에는 해시만 보관한다. 공개 URL과 localStorage에는 관리 토큰을 넣지 않는다.
- 상태 변경 API는 허용 Origin과 관리 쿠키를 확인한다. 타인 캐릭터 ID를 보내도 소유권 검증을 통과할 수 없다.
- 공개 GET은 링크를 아는 사람의 결과 조회에 사용한다. 공개 ID를 안다는 사실로 관리·삭제를 허용하지 않는다.
- 첫 제한안: 일반 API 세션별 60회/분, 쓰기 API 세션별 10회/분, 세션 발급은 IP 기반 별도 제한을 둔다. 이는 비용 완화용 기본값이며 실제 사용·공용 네트워크 오탐을 측정해 조정한다.
- Workers Rate Limiting 바인딩은 위치별·근사 제한이므로 전역적으로 정확한 총량 제한이나 월 비용 상한으로 취급하지 않는다. [공식 동작 설명](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)
- 생성 기능 중지용 설정을 두어 장애·예상 밖 사용량에서 신규 쓰기만 중지할 수 있게 한다. 실제 읽기·기존 공유 결과 제공 여부는 장애 원인에 맞춰 결정한다.
- 운영 로그에는 답변·닉네임·쿠키·관리 토큰·본문을 남기지 않는다. 오류 종류·상태·처리 시간과 집계용 카운터만 기록한다.
- 관리 응답·공개 결과 데이터는 첫 버전에 Cache-Control: no-store를 사용해 삭제 뒤 오래된 결과가 CDN에 남는 것을 피한다. 버전이 붙은 에셋만 길게 캐시한다. 외부 SNS에 저장된 이미지까지 회수할 수 있다고 보장하지 않는다.

## 상세 명세 H. 공유와 접근성

- 카드 제안 크기는 1080×1350px이다. 부모 2개·자식 1개·이름·소개·유전 내역·특수 능력을 포함하고, 긴 문장은 정해진 영역에서 줄바꿈한다.
- 화면과 PNG는 같은 recipe·AssetCatalog·그리기 함수를 사용한다. 버전이 다른 화면과 이미지가 섞이지 않게 한다.
- 이미지와 폰트 로딩 뒤 PNG를 만들고, 준비가 끝나면 공유 버튼을 활성화한다. 공유 버튼 클릭 직후 share를 호출해 브라우저의 사용자 동작 조건을 유지한다.
- 파일 공유는 navigator.canShare({ files })로 지원 여부를 확인한다. 미지원 시 링크 공유 또는 PNG 저장·링크 복사로 전환한다. [Web API 문서](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/canShare)
- 사용자가 공유 창을 닫은 경우 오류 팝업으로 취급하지 않는다. iOS 인앱 브라우저에서 다운로드가 제한되면 이미지 열기·길게 눌러 저장·외부 브라우저 안내를 제공하고 실제 동작을 검증한다.
- /r/:id의 초기 HTML에 제목·설명·og:image를 넣는다. 첫 출시는 공통 OG 이미지이며 개인별 자식 이미지를 미리보기에 넣는 기능은 별도 단계다.
- ‘인스타그램에 바로 게시’ 같은 특정 앱 게시 완료를 보장하지 않는다. 저장·공유 창 열기와 외부 실제 게시를 구분한다.
- 질문은 실제 버튼·라디오 의미 구조로 제공하고 선택 상태·진행률을 스크린리더에 전달한다. 키보드 포커스, 오류 연결, 44px 이상 터치 영역을 확인한다.
- 승인된 화면 색상으로 본문 대비를 검사한다. Canvas에는 생물 설명을 텍스트로 함께 제공하고 중요한 정보를 색상만으로 구분하지 않는다.
- 탄생 연출 기본안은 최대 2초, 건너뛰기 가능이다. reduced-motion에서는 즉시 결과 또는 짧은 페이드로 대체한다.

## 상세 명세 I. 개발 구조와 상태 관리

- 현재 커리어 자료 폴더에는 문서와 시안만 둔다. 개발 저장소가 확정되면 예정 파일 책임 표를 실제 구조에 맞춰 옮긴다.
- 질문 진행·선택·연출 상태는 로컬 상태를 사용한다. 탭 안에서 복구할 질문 초안은 sessionStorage에 저장하고 제출 성공·명시적 초기화 때 지운다.
- 서버 데이터는 TanStack Query 도입을 우선 검토한다. 도입 승인 시 API 조회·mutation·캐시 갱신을 통일한다. Zustand는 첫 버전에서 필요하지 않다.
- 캐시 키는 me/characters, me/results, invite/:id, result/:id로 구분한다. 조합 생성 뒤 me/results를 갱신하고 삭제 뒤 관련 캐시를 비운다.
- Workers fetch 진입점과 API 검증을 분리하고, 순수 유전 엔진은 React·DB에 의존하지 않게 한다.
- 에셋용 assetVersion, 문구용 copyVersion, 조합용 engineVersion, 질문용 quizVersion을 각각 저장한다. v1 데이터는 새 버전 출시 후에도 보관 기간 동안 해석 가능해야 한다.
- 추가 예정 파일: worker/routes/session.ts, characters.ts, invites.ts, results.ts, events.ts; worker/scheduled/cleanup.ts; worker/security/session.ts; src/shared/validation.ts. 기존 저장소에 동등한 모듈이 있으면 재사용한다.

### K-2. 배포 순서

1. 개발·미리보기·운영 환경과 DB를 분리하고 운영 시크릿을 개발 파일에 넣지 않는다.
2. 미리보기 환경에서 마이그레이션과 전체 두 사람 흐름을 검증한다.
3. 운영 DB의 복원 가능 상태를 확인하고 이전 앱과 호환되는 추가형 마이그레이션부터 적용한다.
4. 정적 에셋과 Workers를 배포하고 시작·질문·초대·결과·삭제·공유를 운영 주소에서 재검증한다.
5. 기술 테스트 참가자 10~20명에게 사용할 수 있게 한다. 사용자 초대 메시지 전송은 별도 지시가 있을 때만 수행한다.
6. 오류·사용량·입력 이탈·공유 실패·정성 피드백을 확인하고 문제를 수정한 뒤 공개 범위를 넓힌다.

### K-3. 장애와 롤백

- 배포 전 버전을 기록하고 앱 문제는 이전 배포로 되돌린다. 데이터 손실을 유발하는 DB 롤백을 앱 롤백과 묶어 자동 수행하지 않는다.
- 캐릭터 렌더링 문제는 이전 에셋 버전을 보존해 대응한다. 저장된 결과를 새 파츠로 임의 교체하지 않는다.
- DB 장애에서는 읽기·생성 실패를 구분해 안내하고 재시도를 제공한다. 실패 중 새 결과가 저장됐다고 표시하지 않는다.
- 비용·오류 급증에서는 생성 중지 설정과 요청 제한을 적용하고, 원인을 확인해 복구한다. 설정 변경의 전파 시간도 검증한다.
- 보관 기간 만료 정리·삭제 재실행은 중복 수행해도 안전해야 한다. 백업 복원 뒤 삭제 상태와 엔진 버전 호환성을 다시 검증한다.

**Files:** src/domain/creature/model.ts, generate.ts, generate.test.ts, src/shared/contracts.ts.

- [ ] TraitProfile은 질문 점수에서 정한 성격 축, CreatureRecipe는 파츠 ID·색상 ID, ParentSnapshot은 characterId·traits·recipe·nickname의 고정 스냅샷, OffspringResult는 두 부모 스냅샷·자식 recipe·이름·설명·유전 내역·특수 능력·engineVersion으로 정의한다.
- [ ] 같은 입력·부모 순서 반전에서 동일한 자식, 서로 다른 부모에서 양쪽의 식별 가능한 파츠 유전, 알 수 없는 답변 거부, 호환되지 않는 파츠 배제 테스트를 먼저 작성하고 실패를 확인한다.
- [ ] 정렬한 두 캐릭터 ID와 engineVersion을 기준으로 고정 시드를 만들고, 호환 가능한 파츠와 문구만 선택한다. 유전 내역은 실제 선택된 파츠의 원래 부모 ID에 연결한다.
- [ ] 엔진 수정 후에도 저장된 결과 스냅샷을 그대로 표시하도록 정한다. 기존 조합은 엔진 업데이트를 이유로 새 결과를 생성하지 않는다.
- [ ] 완료 기준: 모든 핵심 테스트 통과, 준비한 12쌍의 결과를 읽고 외형·유전 설명·문구가 일치한다. 검증 후 커밋한다.

### Task 5: 초대·저장·두 사람 조합

**Files:** migrations/0001_initial.sql, worker/routes/, worker/repositories/, src/features/invite/, src/features/result/, 관련 통합 테스트.
**Interfaces:** POST /api/session → 관리 쿠키; POST /api/characters(QuizSubmission) → CharacterView; POST /api/invites → InviteView; GET /api/invites/:id → 공개 InviterPreview; POST /api/invites/:id/pair → PairView; GET /api/results/:id → PublicResult; GET /api/me/results → ResultListPage. 나머지 조회·삭제·집계 엔드포인트와 모든 요청·응답은 상세 명세 F 및 src/shared/contracts.ts의 계약을 따른다.

- [ ] 브라우저별 무작위 관리 세션을 HttpOnly·Secure·SameSite 쿠키로 제공한다. 공개 초대 ID·결과 ID와 관리 권한을 구분하고 수정 API는 Origin·세션을 확인한다.
- [ ] 서로 다른 친구 참여, 부모 순서 반전, 같은 조합 동시 요청, 초대자 결과 재조회, 자신의 초대에 자기 캐릭터로 참여, 만료·삭제 링크, 잘못된 payload·과도한 요청 테스트를 먼저 작성하고 실패를 확인한다.

- [ ] 완료 기준: 별도 브라우저 두 개로 만든 실제 D1 개발 데이터에서 초대·참여·동일 결과 재조회가 동작하고 중복·덮어쓰기·비공개 데이터 노출 테스트 통과. 검증 후 커밋한다.

## 의존 순서와 실행 제안

- 권장 순서: 1 → 2 → 3 → 4 → 5 → 6 → 7.
- 먼저 2·3단계에서 ‘부모 특징이 보이고 결과가 재미있는지’를 확인한다. 해당 기준을 만족한 뒤 화면과 서버 연결 작업을 확장한다.
- 초기에는 상위 에이전트가 한 저장소에서 순차 구현하는 방식을 추천한다. 작은 서비스의 공통 모델·에셋·공유 렌더러가 서로 밀접하기 때문이다.
- 실제 앱 저장소와 실행 방식을 정하기 전에는 현재 커리어 폴더에 앱을 생성하지 않는다.

## 계획 자체 검토

- 캐릭터 생성·양쪽 특성 유전·동일 결과·다중 친구 초대·초대자 재조회·이미지/링크 공유를 각각 담당 단계와 연결했다.
- 초대 링크와 관리 권한을 구분하고 개인정보·멱등성·만료·실기기 공유 실패를 검증 항목에 반영했다.
- 공유 PNG와 OG 미리보기는 서로 다르며 첫 출시에는 기본 OG 이미지를 제공하는 범위를 명시했다.
- 계정 없이 동일 인물을 영구 식별할 수 없다는 한계와 미확정 정책을 사용자 확정 사항으로 포장하지 않았다.
- 새 패키지 설치·제품 코드 작성·인프라 생성·배포는 수행하지 않았다. 이 문서는 실행 계획이다.
